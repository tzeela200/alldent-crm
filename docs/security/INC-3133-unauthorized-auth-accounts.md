## 2. מהו oastify.com

`oastify.com` הוא שרת ההאזנה הציבורי של **Burp Collaborator**, רכיב בכלי בדיקות החדירה
Burp Suite מבית **PortSwigger**. זהו שירות לגיטימי ומוכר, לא תוכנה זדונית.

הכלי מייצר תת-דומיין אקראי חד-פעמי (למשל `6cjq4e4yx2rv4yqelg467bimcdi36s.oastify.com`)
ומדווח לבודק על כל פנייה שמגיעה אליו — DNS, HTTP או SMTP. השימוש המקובל הוא איתור
פגיעויות "עיוורות" (OAST — Out-of-band Application Security Testing).

### הבחנה קריטית

התרחיש הנפוץ, שבו רואים פניות ל-`oastify.com` **בלוגים היוצאים** של השרת, פירושו שהכלי
פעל כ**גלאי** בלבד ולא נכנס לשום מקום.

**זה אינו התרחיש שלנו.** כאן לא נמצאה פנייה יוצאת. נמצאו **רשומות משתמש בטבלת ההזדהות**.
כלומר הכתובת שימשה כ**תיבת דואר חד-פעמית** שקלטה את מייל האימות של Supabase ואפשרה
להשלים הרשמה. השלב של "לבדוק אם קיימת פרצה" כבר הושלם — הושג סשן מחובר.

> **המסקנה המנחה:** השאלה אם הכוונה הייתה לגיטימית אינה משנה את מידת החשיפה.
> חוקר אבטחה הגון לחלוטין, שסרק ללא הזמנה, עדיין קיבל הרשאת קריאה ומחיקה על נתונים
> אישיים של 31,826 אנשים. זהו אירוע חשיפה לפי התוצאה, לא לפי הכוונה.

### 3.3 מדיניות RLS — מה בדיוק נחשף

אומת חי מול `pg_policies`:

| `applications` | Authenticated users only | **ALL** | authenticated | `true` |

`ALL` כולל `DELETE`. `true` פירושו ללא כל סינון. **אין הפרדה בין הבעלים לבין מי שנרשם
מהאינטרנט** — כל חשבון מאומת מקבל בדיוק את אותן הרשאות.

מדיניות `anon` תקינה ומצומצמת כראוי (`job` לפי `job_status=3`, `contact` לפי `profile_token`).

## 4. פעולות ריפוי — סטטוס ביצוע

### ✅ פעולה 1 — בוצעה ואומתה 2026-08-30

הורצה ידנית על ידי הבעלים ב-Supabase SQL Editor, לאחר שהרצה דרך MCP **נדחתה על ידי
מסנן ההרשאות של Claude Code** (כתיבה לסכמת `auth` חסומה).

**תוצאת האימות העצמאי:**

| חשבון | `banned_until` | `deleted_at` | סשנים | refresh tokens |
|---|---|---|---|---|
| 4 חשבונות `*.oastify.com` | `2999-12-31 23:59:59+00` | `null` | **0** | **0** |
| `tzeela200@gmail.com` | `null` | `null` | 25 | 909 |

**בדיקת שפיות שעברה:** לפני הפעולה היו 30 סשנים במערכת, מהם 5 של oastify.
לאחריה לחשבון הבעלים 25. 30 − 5 = 25 ⇒ הוסרו בדיוק החמישה הנכונים, ללא נזק היקפי.
רשומות המשתמש עצמן נשמרו — הראיה קיימת, רק אמצעי הכניסה בוטלו.

**החלטת תכנון:** נבחרה **חסימה ולא מחיקה**. מחיקת משתמש מ-`auth.users` בלתי הפיכה
ומוחקת את הראיה עצמה. חסימה משיגה את אותה תוצאה — מניעת כניסה — ונשארת הפיכה ומתועדת.
מחיקה תמיד אפשרית בהמשך; הכיוון ההפוך אינו אפשרי.

#### פעולה 1 — חסימת החשבונות + ביטול אמצעי כניסה חיים

להרצה ב-**Supabase Dashboard → SQL Editor**:

```sql
begin;

-- INC-3133: נטרול חשבונות oastify.com לא מורשים
-- 1) חסימה (הפיכה; הרשומות נשמרות לצורכי חקירה)
update auth.users
set banned_until = '2999-12-31 23:59:59+00'
where email ilike '%@%.oastify.com';

-- 2) ביטול אמצעי כניסה חיים — קריטי: חסימה לבדה אינה מבטלת refresh token קיים
delete from auth.refresh_tokens
where user_id in (select id::text from auth.users where email ilike '%@%.oastify.com');

delete from auth.sessions
where user_id in (select id from auth.users where email ilike '%@%.oastify.com');

commit;
```

אימות לאחר ההרצה — מצופה `banned_until` עתידי ו-0 בשתי עמודות הספירה:

```sql
select email, banned_until,
       (select count(*) from auth.sessions s where s.user_id = u.id) as sessions,
       (select count(*) from auth.refresh_tokens r where r.user_id = u.id::text) as refresh_tokens
from auth.users u
where email ilike '%oastify%'
order by created_at;
```

#### פעולה 2 — סגירת הרשמה עצמית

זו **הגדרת פרויקט, לא SQL**. זו הפעולה שסוגרת את הדלת עצמה, ולא רק מנקה את מי שכבר נכנס.
בלעדיה ייווצרו חשבונות חדשים מחר.

> Supabase Dashboard → **Authentication** → **Sign In / Providers** → **Email**
> → כבי את **Allow new users to sign up**

זו מערכת אדמין פנימית. אין שום סיבה עסקית שהרשמה עצמית תהיה פתוחה בה.

## 5. חוב פתוח — הסיבה השורשית

חסימת החשבונות מטפלת ב**תסמין**. השורש הוא שמודל ההרשאות מזהה "מחובר" עם "מורשה".

| # | פער | חומרה |
|---|---|---|
| 1 | RLS `ALL / authenticated / true` — כל חשבון מאומת = הרשאות בעלים מלאות | 🔴 גבוהה |
| 2 | `contact_profile_history` אינה שומרת `changed_by` — אי אפשר לדעת מי שינה | 🟠 בינונית |
| 3 | `auth.audit_log_entries` ריק — אין יומן הזדהות כלל | 🟠 בינונית |
| 4 | לא קיים מודל תפקידים (admin / recruiter / viewer) | 🟠 בינונית |

**אזהרה לגבי סעיף 1:** אין להדק את ה-RLS כשינוי חפוז. המערכת כולה מסתמכת היום על
`authenticated = גישה מלאה`. הידוק ללא רשימת היתר מפורשת ינתק את הבעלים עצמה מהמערכת.
זו משימה נפרדת שדורשת תכנון ואישור.

**אזהרה לגבי סעיף 2:** התיעוד ההיסטורי **אינו ניתן לשחזור רטרואקטיבי**. 14,150 השורות
הקיימות יישארו ללא "מי" לעולם. הוספת `changed_by` מועילה מכאן והלאה בלבד.
