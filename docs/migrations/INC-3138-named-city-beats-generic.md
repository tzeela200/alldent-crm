# INC-3138 — עיר עם שם גוברת על "כללי", בלי אישור

**הורץ ב-Supabase: 04.09.2026** · פרויקט `urcdxdcyiedbdwegcebq`
**אושר:** "מאשרת שינוי Supabase עבור INC-3138 לפי ה-Migration שהוצג."

> ⚠ המסמך הזה מתעד מיגרציה **שכבר הורצה**. הוא אינו הוכחה למצב החי —
> ראו [[feedback_migration_not_equals_live]]. לאימות יש לשאול את המסד.

## הבעיה

כשמגיעה רשומה שכבר קיימת אצלנו, ואצלנו העיר "כללי" (1173) ובמקור יש
עיר עם שם — אין שאלה לשאול. העיר עם השם עדיפה תמיד.

**9,900 אנשי קשר מתוך 31,731 יושבים על "כללי"** — כמעט שליש מהמאגר.

`inbox_compute_diff` כבר סיווג את המקרה נכון כ-`'auto'`, וגם לא סימן
אותו כ-`needs_review`. הפער היחיד היה ש-`'auto'` נכלל ב-`v_has_new`,
ולכן ב-`match_inbox_row` התנאי לסטטוס 11 (`AND NOT v_has_new`) נכשל,
השורה נפלה לסטטוס 3 ויושבת בתור — והעיר לא נכתבה עד לחיצה ידנית.

## מה השתנה

פונקציה אחת: `public.match_inbox_row(bigint)`. אין DDL, אין טבלה חדשה,
אין עמודה חדשה.

נוסף בלוק **ג2**, בין חישוב הפער לבין קריאת הדגלים:

1. אם `suggested_updates.city_id.status = 'auto'` — העיר נכתבת מיד
   ל-`contact` או ל-`accounts`.
2. הפער מחושב מחדש **מאותה פונקציה** (`inbox_compute_diff`) — לא שכפול
   לוגיקה. העיר כבר אינה פער, ולכן:
   - אין פערים אחרים ⇒ סטטוס **11** ("קיים במערכת"), יוצא מהתור
   - יש פערים אחרים ⇒ סטטוס 3 עם השאלות האמיתיות בלבד
3. נרשם ל-`inbox_merge_actions` (`action_type = 8`, `approved_by = 'system:auto'`).

נוסף משתנה אחד ב-`DECLARE`: `v_auto_city bigint`.

## גבולות

- **רק `city_id`.** לתפקיד יש ערך כללי משלו (14) אך ההכרעה שם אינה ודאית
  באותה מידה, ולכן נשארת אצל המשתמשת.
- **רק בכיוון אחד**: 1173 ⇒ עיר אמיתית. ההפך כבר חסום (`same`).
- העיר הנכנסת חייבת להתקיים ב-`dict_cities`.
- שורה בסטטוס סגור אינה נפתחת מחדש.
- `region_id` ו-`locality` **אינם** נכתבים —
  `trg_contact_fill_region_locality_from_city` גוזר אותם.

## אימות (הורץ בטרנזקציות עם ROLLBACK)

| בדיקה | תוצאה |
|---|---|
| העיר נכתבה | `city_id = 501` ("כסיפה") ✓ |
| האזור נגזר מהטריגר | `region_id = 3` ✓ |
| ה-diff המחושב מחדש ראה את ה-UPDATE | `city_id` ירד מהפערים ✓ |
| פערים אחרים נשמרו | נשאר רק `facebook_name` ✓ |
| נרשם ביומן | שורה אחת, `system:auto` ✓ |
| **נגד**: שתי ערים אמיתיות שונות | נשאר `diff`, הרשומה לא נגעה ✓ |
| **נגד**: נכנס "כללי", אצלנו אמיתית | נשאר 1020, אפילו לא פער ✓ |

הסיכון שהוצג מראש — האם `inbox_compute_diff` שהיא `STABLE` רואה את
ה-`UPDATE` שקרה רגע לפניה באותה פונקציה — **נבדק ולא התממש**. PL/pgSQL
מקדם את מונה הפקודות בין הצהרות, ולכן ההצהרה הבאה רואה את השינוי.

## Rollback

שחזור הגרסה הקודמת של `match_inbox_row` — היינו הסרת בלוק ג2 והמשתנה
`v_auto_city`. אין שינוי סכמה להחזיר.

## לא נכלל

**Backfill.** שורות שכבר ישבו בתור עם `auto` לא שונו למפרע. תיקון נתונים
בייצור דורש אישור נפרד.
